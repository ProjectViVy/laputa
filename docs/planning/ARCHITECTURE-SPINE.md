# 架构骨架：Garden 作为 Hermes 的薄人格治理扩展

状态：计划稿 / CONCERNS；产品实现未授权。源码依据 [HERMES-SOURCE-AUDIT.md](HERMES-SOURCE-AUDIT.md)，内部合同见 [CONTRACTS.md](CONTRACTS.md)。本文是唯一详细架构，不另起通用框架。

## 旧Go架构仅作参考，新代码按最新决策重写

所有者澄清：旧Go版可能已经具备完整闭环，可以参考其设计经验，但新实现应按最新的Hermes-first决策重写。语言、宿主与职责边界已经变化，不把旧代码作为继续开发的基线，也不做逐行翻译或机械复刻。

已定位的旧main `9acc999301d5d575da2cea902a1c6d213763f381` 中，演化流程、Collect / Apply / Lookup、回执和故障处理可用于回答具体设计问题；必要时再查看最后候选分支及历史验收。它们是参考材料，不是新实现必须照搬的合同，也不把旧版全量重验设为新开发的必经前置。

新代码以Python/Hermes原生扩展方式重新实现，实际复用的是Hermes当前支持的能力。旧闭环中适用的思想与验收场景可以吸收；旧Go包、服务、存储格式、Effect结构、审批策略、调度和API均不自动继承，不建立兼容层或迁移路径。是否采用某项旧设计，由新需求和当前宿主证据决定。

## 选择

**独立分发的薄原生Python插件 + 操作技能 + 显式本地命令。** 不修改当前Hermes core，不注册memory/context provider，不建立Web/MCP/REST；初始候选切片不提供模型可调用apply工具，不自动订阅hook。

技能说明何时反思、如何选证据；插件负责确定性的绑定、校验、候选/回执和冲突状态。Skill提示词不能承担R04/R05的强制边界。

```text
受信任本地操作者选择获准可见证据
    ↓ 固定home / 用途 / 来源，不让模型补授权
Garden校验输入与原生权威基线
    ↓ ctx.llm：有界逻辑归纳，无工具循环
分类候选 + 出处 + 反例 + 差异 / no-op
    ↓ 独立校验 / 已冻结采纳策略
[真实写入关卡：P0待决]
    ↓ 原生SOUL应用 / 回读 / 未知状态对账
[生效关卡：新验收会话，不接管当前prompt缓存]
    ↓ 私有结果与有条件回滚证据
```

## 组件（均为拟新增路径，当前未创建）

| 路径 | 责任 |
| --- | --- |
| `plugin.yaml`, `garden_hermes/__init__.py` | 声明与命令注册；register不启动任务/模型 |
| `garden_hermes/domain.py` | 内部类型、独立校验、纯状态转移 |
| `garden_hermes/host.py` | 真实home/入口绑定，原生ctx.llm封装 |
| `garden_hermes/store.py` | 私有候选、intent、回执的原子文件存取 |
| `garden_hermes/proposal.py` | 有界归纳、分类、证据引用核验，无SOUL写能力 |
| `garden_hermes/review.py` | 许可/候选基线检查；无默认自动采纳 |
| `garden_hermes/apply.py` | 关卡通过后的受限原生SOUL应用/恢复 |
| `garden_hermes/activation.py` | 能力检测和新会话激活证明 |
| `skills/garden/SKILL.md` | 操作指导，不是权限执行层 |

无独立数据库/ORM；元数据用profile私有文件。before/after是恢复记录，不独立加载为运行人格。原文不进公开仓库。

## 选型理由

- Skill-only能说明流程，不能独自保证确定性范围、幂等和回执，不作为完整首期。
- Observer payload可能带原文/系统提示/历史，超时也不撤销迟到副作用；首期不自动采集。
- Curator维护skills而非SOUL；分流复用，不把技能维护冒充人格成长。
- provider/context engine/提示词section会接管或复制原生责任；不选。
- 没有第二消费者，不先做独立服务、队列或SDK。

## 已冻结的设计边界

1. 运行人格只认绑定home的SOUL；不改其他profile，不以cwd/profile_name授权。
2. 首期面向受信任本地操作者；未知surface/home和远程入口拒绝。此规则不是对同一OS用户任意Python/shell的安全沙箱。
3. 模型仅返回受限候选，无执行工具或授权字段。ctx.llm不是松柏完整会话，不自动附带全部人格/历史。
4. 只用显式获准文本，不扫全库、不采隐藏推理。用户事实/技能候选指向原生路径，首个writer只处理SOUL。
5. register、查看、拒绝和no-op不调用模型。归纳至多一次逻辑调用；宿主可能物理重试，不声称仅一次上游请求。记录真实usage，不编造硬费用上限。
6. 先durable intent，再目标写入，再回读和结果；崩溃后对比精确before/after/current，不盲目重试或回滚。元数据与SOUL不是跨文件ACID。
7. 不改当前缓存prompt。先用明确的新验收会话；当前版本没有refresh-prompts，不用repair-prompts偷换，也不擅自升级。
8. 真实人格/证据读取、模型调用、写入和生效试验都需后续授权；本轮只查源码。

## P0待所有者决定

### D01：采纳策略

建议首轮“我自主生成、操作者显式采纳”，验收闭环后再为稳定人格增量开放有限自动采纳。另一选项是首期即规则内自动采纳，但必须先冻结可写范围、否决和恢复策略。任何候选都不能扩大工具/管理员/隐私权限。建议不等于已获批准。

### D02：非合作写者并发

原生SOUL PUT是原子写，不是CAS。桌面、文件工具、外部编辑器未统一参与同一锁；插件锁+写前重读仍有检查后竞写窗口。

- **A：受控独占维护窗口（轻量建议）**。所有者明确暂停其他人格编辑路径；只在此支持范围内应用，漂移即拒绝。不宣称防住任意编辑器竞写；这缩窄R05，须明确同意。
- **B：完整跨原生入口版本写合同**。先研究/推动Hermes统一写入与expected-version接口，成本/影响更大，不能伪装成薄插件已经提供的能力。

D02未定前，G04不实现SOUL写入，完整闭环不Ready。具体原生调用接口要在所选合同下确认，不把REST handler当可直接import的领域服务。

## 激活与验收

回读只证明persisted。G05先在合成隔离profile中证明新session的实际请求身份块采用预期内容，再在获准的真实松柏验收会话复核；私有记录会话与版本、安全摘要，不公开完整system prompt。模型回答“我变了”不单独构成证明。

旧会话保留快照应报告persisted_not_effective，不强制压缩/重启来制造成功。长会话热刷新后置；升级能力需单独授权和验证。

## 成本

显式、按批、无热路径hook、全库扫描或常驻任务。证据/输出尺寸和超时作为明确配置做边界测试，不虚构未测延迟/token目标。真实数据保留/删除策略在试验前冻结，不级联删除原生记忆。
