# 原文全文

> **[批注 · 开头]** 这套系统的逻辑图（用户消息 → 浅层召回 / 深层管道 / L0 原文归档）与我们的 Recall 架构同构：默认浅层保证延迟，显式深层走多路融合。注意它的 L0 归档是「永不丢失」的第一优先——这正是我们 Mentle Raw-first 的「原文先落地，LLM 压缩是可选派生」。

## 一、整体架构

在讲具体内容之前，先把整个系统的逻辑图画清楚。

```
                        用户消息
                           │
          ┌────────────────┼────────────────┐
          ▼                ▼                ▼
    浅层召回通路      深层管道（异步）      L0 原文归档
          │                │                │
          │                │                ▼
          │                │           JSONL 纯文本
          │                │           永不丢失
          │                │
          │      ┌─────────┼─────────┬──────────┐
          │      ▼         ▼         ▼          ▼
          │     L1         L2        L3         L4
          │   语义提取   场景归纳   用户画像   知识图谱
          │      │         │         │          │
          │      │         │         │          │
          │      └─────────┼─────────┴──────────┘
          │                │
          │                ▼
          │         MemPalace 本地库
          │         ┌───────┼───────┐
          │         │       │       │
          │         ▼       ▼       ▼
          │     drawers  closets   KG
          │     7,635    2,096   6,077
          │         │       │       │
          │         └───────┼───────┘
          │                 │
          │    ┌────────────┼────────────┐
          │    ▼            ▼            ▼
          │  向量检索    BM25 关键词   KG 关系
          │  (bge-m3)   (FTS5分词)   (SQLite)
          │    │            │            │
          │    └────────────┼────────────┘
          │                 │
          │                 ▼
          │          融合排序 & 去重
          │                 │
          └────────┬────────┘
                   ▼
            上下文注入 Agent
```

两条通路，一个底层。

左边浅层——日常对话走这条，bge-m3 本地嵌入 → ChromaDB 向量检索，<200ms 返回。右边深层——定时异步管道，L1 语义提取调用 DeepSeek API（唯一出设备的数据），L2-L4 全部本地计算。底层共享 MemPalace，不存两份。

> **[批注 · 浅层/深层]** 「不存两份」与我们的原则一致：召回通路共享同一个材料库，不复制数据。它把 L1 语义提取（唯一出设备）定位为可选增强——对应我们「LLM 压缩是可失败、可跳过的派生优化」，不是持久化前提。

平时 90% 的对话靠浅层。 用户说「认真回忆 / 深度检索 / 回忆一下 XX」，触发深层全管道——融合向量 + BM25 + KG 三条检索线，汇总排序后注入 Agent。

> **[批注 · 触发机制 ⛔]** 这里明确写「不是靠 LLM 自己判断」——它退而求其次用系统 prompt 触发词匹配。我们不做 prompt 层判定：`/v2/recall/fast` 与 `/v2/recall/deep` 是显式工具边界，触发词最多作为 host 层翻译，判定权在工具调用，可审计、可治理。它自己也承认触发词不可靠，我们只是走得更彻底。

## 二、我理解的长记忆

不是「存得多、记得久」这么简单。我给长记忆的定义是三条：

第一条，丢了能回来。 Agent 崩溃、系统重装、索引损坏——记忆库能不能独立存活？

7 月 9 日 ChromaDB 索引损坏，我删掉整个向量 collection，从 SQLite 导出全部 7,635 条 drawer，5 分钟重建。Agent 重新上线后，回忆精度和重建前一致。后来 MemPalace 从 3.3 升到 3.5，bge-m3 的 monkey-patch 被破坏，整库需要重新初始化——因为 L0 原文都在，管道重跑一遍就恢复了。

> **[批注 · 可重建性 ✅]** 这就是「派生层可重建」的实战证明：向量索引、KG、结构化记忆全是投影，只有 L0 原文是唯一真源。对应我们：Mentle 材料库 + 可重建索引；运营台「数据健康」轴应暴露 embedding model version / dimension / last rebuilt / rebuild duration。

OpenClaw 有一次版本升级后出现兼容问题，不得不回退。升级过程中部分配置被覆盖，索引需要重建。但因为 L0 的 JSONL 原文和 MemPalace 数据库完全独立于 OpenClaw 运行环境——回退折腾了一圈，记忆库毫发无损。

> **[批注 · 环境分离 ✅]** 记忆库独立于宿主运行环境存活——正是我们 Laputa/Mentle 与 host adapter 分离的原则。运营台应显示 L0 完整性与可迁移性状态。

换一台新电脑也一样。 把 ~/.mempalace/ 和 JSONL 原文目录复制过去，装好依赖，记忆水平立即恢复。不需要重新「喂」数据、不需要重新训练——你的记忆库就是几个文件夹。

> **[批注]** 「记忆库就是几个文件夹」= local-first 的最高形态。我们的迁移设计应保证同样性质：复制数据目录即完成迁移，无重训练、无云依赖。

第二条，跨天能精准回忆。 不是模糊匹配，是精确回溯上下文和结论。

4 月 30 日我跟 Agent 讨论过一个项目架构方案，做了具体决策。7 月 23 日——隔了 84 天——我问「上次那个架构方案我们最后是怎么定的」，Agent 能准确回应当初的讨论内容、决策理由和最终结论。靠的是 L0 原文定位时间范围 + L1 结构化记忆提取事实 + L4 知识图谱补充实体关系。

> **[批注]** 跨天精准回忆 = L0 时间定位 + L1 事实提取 + KG 实体补全的组合。我们的 Deep Recall（KG/timeline 扩展 + RecallTrace）正是同构能力，且多一层：每次深度召回都留 trace，可回放「为什么召回、读了什么」。

没有长记忆的 Agent 面对这种问题，能做的只是翻最近几十轮对话——超出上下文窗口的内容完全不可见。有这套系统之后，84 天前的讨论和昨天的讨论，检索路径是一样的。

第三条，一句话触发深度检索。 用户不需要写搜索 query，不需要知道数据怎么存的。

这里有一个容易被忽视的设计细节：Agent 怎么判断什么时候该走浅层、什么时候该走深层？不是靠 LLM 自己判断——那不可靠。实际做法是在系统 prompt 层做触发词匹配：当用户消息中包含「认真回忆」「深度检索」「回忆一下」「还记得吗」「查一下」等模式时，Agent 自动切换到深层检索通路。其他情况默认走浅层，保证日常对话的响应速度。

> **[批注 · ⛔ 重复强调]** 与前面批注一致：它承认 LLM 自判不可靠，但解决方案仍停留在 prompt 工程。我们把它升级为显式 API 边界，这是架构级差异，不是措辞差异。

触发后不是一次简单的向量搜索，而是一个多步检索流程：

用查询语句在 L0 JSONL 原文中定位相关时间范围（纯文本扫描，零成本）
用 bge-m3 在 L1 结构化记忆中做语义检索，提取匹配的 drawers
用 L4 知识图谱补充关联实体——查到「架构方案」，KG 反向查出相关的「项目」「后续决策」
三条线结果汇总，按融合分数排序（向量相似度 × BM25 关键词 × KG 关系权重 × 时间衰减）
去重后注入 Agent 上下文
整个过程对用户来说就是一句话。深层检索延迟 <500ms，因为嵌入和索引全在本地，没有网络往返。

> **[批注 · 融合排序 ✅]** 多路召回 + 融合排序 + 去重 = Mentle hybrid search（向量 × BM25 × KG）+ RRF 融合的同构设计。它加入时间衰减，我们以 heat/时间衰减参与排序建议，但不允许独自裁决真值。

这不是 prompt engineering 的技巧，是系统架构自然支持的能力。

> **[批注]** 这句话是整篇文章的题眼，也是我们的立场：能力来自系统架构（Raw-first、分层召回、可重建投影），不是 prompt 技巧。

## 三、为什么端侧

苹果这几年一直在推端侧 AI 的理念——数据只在设备上处理，就不存在集中式的攻击点。他们做的是端侧推理（Apple Intelligence 在 iPhone 上本地运行模型），我做的是端侧记忆。逻辑是相通的。

对于 AI Agent 来说，记忆系统选端侧有三个实际好处：

安全上，对话记录、嵌入向量、知识图谱全在本地硬盘。没有第三方服务器持有你的对话历史。唯一出设备的是 LLM 推理的 prompt——传出去的是问题，不是记忆库。

> **[批注 · 隐私边界 ✅]** 与我们一致：唯一出设备的是受治理、最小化的请求；记忆库本体永不出设备。我们的 Evolution Evidence Bundle 原则同源：出设备的是最小、脱敏、可追溯的证据，不是私库。

效率上，记忆检索没有网络往返。嵌入用本地 Ollama 的 bge-m3 算，向量检索在本地 ChromaDB 跑。<200ms 的响应时间是可控且可预期的——不依赖 API 服务商的限流策略和网络状态。

成本上，嵌入和检索零边际费用。84 天里记忆模块做了数千次检索，账单为零。云端记忆方案按检索次数收费——这个成本会随着使用量线性增长，而本地方案的成本是固定的（硬盘空间 + 偶尔的嵌入计算）。

苹果的路线验证了端侧的方向，但他们的重点在推理。我的看法是：对于需要长期陪伴的 AI Agent，端侧记忆和端侧推理同等重要。

## 四、嵌入和检索的自主权

这里容易被误解为一个浅显的问题——「你是不是想说本地部署比云方案好？」不是。我想讲的是：记忆系统里有两个容易被忽视的组件——嵌入模型和检索算法——它们对最终召回质量的影响比 LLM 本身更大。

> **[批注 · 召回质量底线]** 「嵌入与检索决定召回质量底线，LLM 再好，召回不对回答就不可能对」——这是对 Garden/Mentle 工程重点的佐证：检索基础设施是质量底线，LLM 是上层。运营台应把嵌入模型版本、检索算法版本作为一等状态展示。

云端方案通常把这两个东西打包成黑盒。你传对话进去，服务商决定用什么嵌入模型、用什么检索算法。大部分英文嵌入模型对中文的语义区分能力很弱——「Apple」和「苹果公司」的语义距离，在英文嵌入模型里可能比在中文嵌入模型里大得多。但在云端方案里你没法换嵌入模型。

我做了两件事：

嵌入层： 把默认的 384 维英文模型换成 bge-m3（北京智源，1024 维）。同一个搜索 query「系统架构设计」，换之前召回的只是包含这些关键词的片段，换之后召回的是语义上真正讨论架构设计的片段。中文场景下这是质的差距。

检索层： 不用单一的向量相似度排序。融合了三条线——向量语义（bge-m3）、关键词匹配（SQLite FTS5 + CJK 中文分词）、知识图谱关系权重。跨天回忆场景下，纯向量检索容易把时间久远但语义相近的内容排在前面，融合排序可以通过关系权重和时间衰减修正。

> **[批注]** 中文场景下嵌入模型选择与融合检索是质变因素——这是 Mentle 检索层应固化的经验：默认中文语义嵌入（bge-m3 系）、BM25+FTS5 CJK 分词、KG 关系权重、RRF/融合排序。

这两个东西跟用哪个 LLM 没关系。它们决定了记忆系统的召回质量底线——LLM 再好，召回的内容不对，回答就不可能对。

## 五、踩过的坑

坑一：换嵌入模型，ChromaDB 直接罢工
bge-m3 替换默认嵌入模型后，ChromaDB collection 的维度一旦创建就不可修改。旧 collection 锁死了 dimension=384，MCP server 检测到 384≠1024，拒绝初始化。解法是导出全部数据 → 删除旧库 → 重建 → 重新嵌入。7,635 条，全自动 5-10 分钟完成。

> **[批注 · 索引可重建性 🔧]** 向量索引的 schema（维度、模型版本）不可原地变更，重建是常态运维动作。我们的运营台「数据健康」轴必须显示：embedding model / dimension / last rebuilt / rebuild duration / rebuild status，并把重建流程做成可审计的日常能力。

坑二：OpenClaw 升级，回退重建，记忆没丢
有一次 OpenClaw 版本升级后出现兼容性问题，不得不回退到旧版。升级过程中部分配置被覆盖，索引需要重建。但因为 L0 的 JSONL 原文和 MemPalace 数据库完全独立于 OpenClaw 运行环境——回退、重建折腾了一圈，记忆库毫发无损。Agent 重新上线后，对话上下文和跨天回忆能力没有任何损失。

> **[批注 · 环境分离 ✅]** 同前：宿主升级/回退不应影响记忆库。我们的 host adapter 层应保证同样隔离，运营台显示 L0 完整性与「是否独立于 host 存活」状态。

坑三：Mac 休眠，8 个定时任务全停
launchd 的 StartInterval 在 Mac 合盖休眠后不补跑。早上打开电脑，所有 pipeline 日志断档，审计面板全红——不是功能坏了，是定时器被冻住了。解法是在每次系统触发时加唤醒检测——扫描日志时间戳，断档超阈值的当场补跑。每天早上第一条消息触发自愈，无需人工干预。

> **[批注 · 断档自愈 🔧 重要]** 这条对我们的 Garden 定时管道（report loop、ingest、spool drain）有直接工程价值：需要「唤醒检测 + 时间戳 gap 阈值 + 幂等补跑」。这也是运营台 Overview 数据健康轴的实时信号：pending_mentle、索引 backlog、报告断档、pipeline 断档。我们比它更进一步：补跑必须幂等（event_id + content_hash 回灌），不能重复注入。

## 六、84 天真实数据

指标	数据
记忆跨度	84 天（4.30 — 7.23）
结构化记忆	7,635 条 drawers，按项目/话题/时间自动分类
知识图谱	6,077 个活跃三元组，支持时间线查询
L0 原文	97 个文件，6,136 条 JSONL，18MB
记忆库体积	194 MB（drawers + closets + KG + 向量索引）
检索延迟	浅层 <200ms，深层融合 <500ms
检索成本	零——嵌入和检索全程本地

> **[批注 · 规模参考]** 这些数字是运营台容量规划的参考量级：数万条结构化记忆、数千三元组、约 200MB 全库、毫秒级延迟。Garden 运营台应能在一台普通机器上承载同级规模并展示对应指标。

同样的任务，有没有长记忆的差别：

Agent 收到「我们之前讨论过的那个架构方案后来怎么定的」——

没有长记忆：只能搜索最近对话窗口（几十轮）。超出上下文的讨论完全不可见。回答要么是「我没有找到相关信息」，要么更糟——编一个听起来合理但错误的内容。

> **[批注 · 幻觉抑制]** 「没有长记忆 → 编造合理但错误的内容」——长记忆系统是 Agent 幻觉抑制的基础设施之一。我们的 RecallTrace 更进一步：每次召回可回放证据链，「为什么这么回答」可审计。

有长记忆：Agent 从 L0 定位到 4 月 30 日的对话 → L1 提取决策要点 → L4 补充项目实体关系 → 回答精确到具体的讨论时间和结论。

成本角度看： 云端记忆方案按检索次数收费——每次 Agent 调记忆都是一次 API 调用。我这套系统 84 天里，记忆模块做了数千次检索，费用为零。同时，因为 Agent 有稳定的记忆上下文注入，每次对话不需要用户重复解释背景——LLM 推理的 prompt 更紧凑、更可预测，缓存命中率自然更高。

> **[批注]** 「稳定上下文 → prompt 更紧凑、缓存命中更高」——我们的 ContextView 装配（Frozen Core + STM + scoped WORLD，而不是全量注入）天然支持这一点：确定性、可缓存、可降级。

## 七、设备友好

Mac 和 Windows 上都验证过可行。没有特殊硬件要求——嵌入模型通过 Ollama 运行，有 GPU 更快但不是必须。没有特殊硬件要求。除了 LLM 语义提取需要调 API，记忆的存储和检索是零费用、零网络依赖的。换新设备时，复制两个文件夹就完成迁移。

> **[批注 · 结论]** 端侧长记忆的完整论证：安全（本地）、效率（无网络往返）、成本（零边际费用）、设备友好（无特殊硬件）、可迁移（复制目录）。这是 Garden/Mentle local-first 的行业侧实证。
