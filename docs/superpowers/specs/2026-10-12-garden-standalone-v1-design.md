## 1. Outcome, scope and evidence

Garden becomes a standalone, local-first application for managing multiple independent persona subjects and their memories. It has one canonical memory backend and one active owner, a full management console, and explicitly activated external-host adapters. Existing VIVY remains one subject and must use the same identity authority visible in Garden. Multiple subjects are not multiple human accounts. The initial target is a trusted single-owner local installation, consistent with issue #8. API separation does not sandbox arbitrary code with filesystem/database/administrator access; remote or hostile multi-tenant hosting is excluded.

Apply 多快好省: reuse the Go modular monolith, Laputa Markdown authorities, Garden agent API, existing console, exact memory scopes, Mentle adapter and BML library. Add no proxy, broker, external identity server, new agent runtime, scheduler, general plugin marketplace or duplicate memory engine. Basic selected experience → usable fact is included; autonomous persona/rule/skill evolution is excluded. Tencent is a functional UX benchmark, with no API compatibility, L0–L3 taxonomy, team IAM or four-service architecture requirement.

## 2. Architecture choice and responsibility boundaries

| Approach | Benefit | Cost/decision |
| --- | --- | --- |
| Extend existing modular monolith with central registry/policy and thin adapters | Reuses authority, UI, transports and storage; one local service; a single authorization boundary | **Recommended.** Requires route convergence and explicit owner handoff. |
| Keep independent embedded owners and aggregate their UIs/stores | Smaller first UI patch | Reject: does not deliver unified canonical memory or solve writers, isolation and revocation. |
| Introduce memory gateway/proxy plus independent identity and integration services | Broad interception and deployment options | Reject: unnecessary services, credentials and capture surface; poor consent fit. |

Proposed dependency direction:

```text
Console / HTTP / Garden MCP / embedded trusted client / host adapters
                              |
                Garden agentapi application boundary
              auth -> binding -> membership -> scope -> operation
                  /             |                 \
       subject registry      Laputa             memory.Backend
       host/setup state      Persona + Recap    selected adapter only
       (Garden state DB)     (Markdown owner)    Mentle OR BML canonical DB
```

No transport owns business policy. Extend existing `garden/agentapi`, `garden/internal/runtimecore`, `garden/memory` and console modules. Proposed new packages: `garden/internal/registry` (profiles/shared spaces/membership/host bindings), `garden/internal/hosts` (file plans/adapters/status), `garden/internal/setup` (wizard/secrets/upgrade coordination), `garden/backends/bml` (adapter over the existing BML Go module). These paths do not yet exist. Keep registry, membership, host state and setup in the existing Garden state SQLite database. They are control metadata, not a second memory-content database. Backend mutation receipts stay transactionally owned by the selected backend. Laputa revision metadata stays with Laputa.

Reuse existing local ownership/lifecycle facilities, adding only an OS lock for authority paths where currently missing. One process opens each subject authority once; no lease service, distributed fencing or new ownership daemon is proposed. Subject handles share the selected backend connection pool; they must not each run index rebuilders or ingestion workers. Host integrations use authenticated calls to that process. Embedding remains available as a mutually exclusive deployment composition for existing VIVY/DIVA use; an embedded and standalone owner cannot open the same installation concurrently. Explicit absolute paths and failure-on-misconfiguration are preserved.

## 3. Identity, persistence and ownership

### 3.1 Distinct identities

| Entity | Proposed key and meaning | Never implies |
| --- | --- | --- |
| Persona subject | Existing stable `ProfileID`; same value is private memory `SubjectID`; retain identifiers such as `diva` | Permission, agent process, workspace or login |
| Principal | Authenticated human session, trusted host handle or per-host credential binding; a unique client key distinguishes callers without a new identity hierarchy | A subject selected in request JSON |
| Runtime agent | `AgentID` and platform supplied as validated provenance | Authentication or grants |
| Host binding | `BindingID`, principal, selected ProfileID, approved workspace tuples and three independent controls | Activation from install/discovery |
| Workspace | Opaque registered workspace ID with owner-confirmed local path mapping | Universal sharing; empty workspace is exact personal scope, not wildcard |
| Session | Host-instance-qualified session ID bound on admission; subject and operation ceiling fixed; live membership re-resolved | A separate subject, Recap or cross-workspace entitlement |

Retain existing valid subject identifiers such as `diva` when explicitly attaching that authority. Never use arbitrary imported IDs directly as filesystem path components; new directory names are validated opaque IDs and existing authorities use the separately approved canonical path. New subjects get random IDs; display names are editable and non-authoritative. An existing alias is not globally unique evidence: registration also checks authority location and installation identity. A repeated attach of the same authority resolves to the same subject; an ID collision from another installation is an explicit conflict, never merged by name.

### 3.2 Proposed data layout

```text
<GardenHome>/garden.db                  registry/membership/bindings/setup metadata
<GardenHome>/subjects/<ProfileID>/      Laputa config root for a new subject
  persona/                             existing Persona owner layout
  actmem/ACTMEM.MD                      existing ACTMEM location; proposed v3 body
<GardenHome>/memory/                    ONE selected backend's canonical store
<GardenHome>/secrets/                   host-side credentials; never served as content
<GardenHome>/backups/                   explicit local backups/host write recovery
```

These are proposed defaults, not mandatory relocation of existing data. `persona.Open(configDir)` already appends `persona/`, and `actmem.New(configDir)` appends `actmem/`; registry paths identify their common config root, not an extra copy of either leaf. Registry rows hold an approved canonical absolute authority path, backend installation ID, owner mode and current lifecycle state. Existing paths may stay in place after owner handoff. No registry copy of Persona or Recap bodies is editable. Preserve seven ADR-0012 Markdown documents plus existing human-controlled `MISSION.MD`; retain six Frozen Core projections and Mission v2. WORLD is tool-only; ACTMEM is never Frozen Core. Symlink/canonical-path identity must be checked before attach, and one authority path cannot be registered as two subjects.

### 3.3 Existing VIVY/Garden and other-machine data

Attachment is an explicit transaction-like workflow with persistent checkpoints: inventory → owner choice → stop/drain old writer → snapshot → acquire locks and validate → register → enable new client → verify → finalize. Discovery may inspect only owner-selected locations or explicitly approved standard homes; it never imports or activates. Reuse wizard progress and existing backup/config records for source paths, subject mapping, schema/version, backend and prior owner. A new transfer ledger/manifest framework is unnecessary.

For an existing VIVY/DIVA embedded Garden, the selected mode is **standalone takes ownership, VIVY becomes an authenticated client**. Preserve the same Persona directory, revisions, Recap and selected canonical database. First ship the client composition and ownership fence in VIVY; only then offer takeover. Old direct library opening must refuse while the standalone owner holds the OS lock. An explicit client/embedded mode in existing configuration prevents accidental old-mode restart; the local lock prevents concurrent supported writers. Existing older binaries that do not honor the mode/lock cannot be considered safe clients: stop them and require the supported version before takeover. A filesystem path alone is insufficient.

If Garden already uses a different memory database, it cannot simply attach another active database and call them unified. Offer: (a) use the existing installation as the entire Garden installation after takeover; or (b) explicit reviewed import into the currently selected writer, with source identity map, provenance, conflict inventory, dry-run counts and backup. No automatic BML→Mentle conversion. A source that remains active after a snapshot is labeled independent; it is not a second writer to the same persona. Reusing the same persona across VIVY and Garden requires actual client handoff, not snapshot import.

Other-machine data requires an owner-exported, versioned bundle and explicit import/ownership transfer. v1 proposes no live cross-machine filesystem sharing, synchronization or remote takeover. Until transfer is confirmed, display an attachment candidate with no active persona/binding. Interrupted handoff resumes from durable checkpoints and keeps writes disabled when ownership is uncertain. Rollback requires stopping the new owner and restoring an identified coherent backup; never auto-resume the old writer after new commits.

## 4. Authorization and the native Garden API

### 4.1 Trusted bindings and named shared spaces

Use the existing trusted in-process client handle, or one opaque credential per opted-in external host mapped server-side to its `ProfileID`, workspace and allowed operations. Persist only credential digests in Garden; plaintext stays in the designated host secret location. Reuse authenticated human control-plane behavior, with protected local pairing/session handling where needed; no reusable admin token in URLs, synced instruction files or browser localStorage. Loopback location or a shared role-class token alone never selects every persona. No identity provider, signed/self-contained capabilities, general policy language, per-record ACL or token-delegation chain is proposed.

The human owner manages profiles and named shared spaces in the existing control-plane database. Each membership is simply `(SharedSpaceID, ProfileID, read | read_write)`. Only the human changes membership. A trusted host's operation controls can narrow membership but never widen it. A profile reads/writes its authorized exact private scopes; workspace membership never opens another profile's private data. Shared-space `read` allows search/expand; `read_write` also permits explicit create/update/delete in that space with ordinary CAS and receipts. No complex shared editing roles are required. Persona and Recap remain subject-private, outside shared spaces.

**Proposed minimal shared-scope mapping:** reuse `scope/v1` exact encoding with a registry-owned reserved storage key `SubjectID = shared:<opaque-space-id>`, `Kind = personal`, empty WorkspaceID. This key denotes a shared resource, never a registered persona or session ProfileID. The resolver alone creates it and verifies membership; reserve the prefix against new ProfileIDs and refuse a legacy collision pending an explicit decision. This is a narrow interpretation delta to the existing storage tuple, not a new subject hierarchy or `scope/v2` migration. Source inspection confirms the current encoder/validator accept opaque nonempty IDs; implementation must validate this mapping through affected adapter callers. Existing private records keep their exact scopes and are never reclassified. Originating ProfileID/agent/session remain provenance on shared writes, distinct from the shared storage key.

Ordinary capture, automatic recall follow-up, summarization and Persona/Recap updates write only to their originating private scope. The user explicitly selects a shared space and the information to place there; v1 can create a new shared record, with provenance, without supporting in-place publication/movement of a private record. A private source link does not grant readers access to that source: expand only what their current binding permits and indicate unavailable lineage without disclosing private metadata. No run-wide taint, inherited ACLs on every derived fact, automatic declassification workflow or prevention of all model paraphrasing is claimed.

Persona-free workers reuse the host's existing bounded execution handles and explicitly selected material. No automatic Persona, Recap or sharing membership is inherited. If an external worker needs service calls, the human/trusted host binds a minimal supported handle with the existing operation limits; no recursive capability delegation framework is needed. Same-subject persistent-session admission remains separate from a role label.

### 4.2 Enabled-path semantics and minimal convergence

Every enabled data-bearing operation authenticates, resolves the binding and current membership, validates the exact read/write scopes and bounds, invokes the owner, then validates scope/status/revision before disclosure. Include automatic bootstrap/recall and model context assembly, not only explicit tools. Carry originating ProfileID, session and exact write scope through capture, spool, retry and restart; reuse existing idempotent work records. Re-resolve membership on new calls and before queued writes or Garden-managed context reuse. On membership removal, invalidate affected existing handles/cursors/projections or make them re-resolve; add no policy cache, global concurrency guard or distributed authorization layer. Requests admitted before removal may finish; calls admitted after removal are denied. Already delivered context is not retractable, and must not be re-injected as newly authorized Garden context.

Reuse existing `/v2` routes, DTOs and `agentapi` operations where sufficient. Add only missing profile selection, shared-space membership, host/setup and full UI operations alongside them; a wholesale `/api/garden/v1` namespace rewrite is not a prerequisite. Native Garden APIs have no Tencent wire compatibility. The human UI selects an owned profile; external calls resolve it from the trusted binding, never request-body authority claims.

| Operation family | Required behavior on enabled surfaces |
| --- | --- |
| List/search/collections/counts | Exact authorized private/shared scopes; filter status/scope before disclosure, including stale-index results; no private names/counts. Revalidate cursors after membership changes. No mandatory vector partition or native pre-filter rewrite: measure representative recall usefulness and fix concrete failures minimally. |
| Get/expand/lineage/history | Recheck exact record and linked-source visibility, expected revision and tombstone state. An old card/ID never bypasses current membership. |
| Create/edit/delete | Private target belongs to bound ProfileID, or explicitly selected shared target has current read_write membership; scope immutable on ordinary edit; preserve expected absence/revision, operation ID/digest and receipts. |
| Mutation lookup | Resolve authorized target scope before backend lookup; no foreign receipt disclosure. |
| Persona/Recap | Bound subject access plus owning Laputa CAS/history and existing human/agent operation distinctions; never implicitly shared. |
| Optional graph/timeline/trace/global enumeration | May return explicit unavailable for multi-persona agents if cheap correct scoping is absent. Preserve existing single-persona capabilities. The required human memory/history/lineage UI still uses authorized operations. |

Retained memory CRUD, search, evidence, deep recall and MCP calls converge on Garden policy; remove their bypasses when replaced. Optional endpoints need not all be rebuilt merely to stay mounted: deny unsupported multi-persona access explicitly. Direct Mentle MCP is not a persona boundary and is not exposed as an agent path against the Garden-owned DB. Keep independently useful Mentle library/CLI facilities and existing single-persona functions. Agents with direct filesystem/database/admin access are outside this trusted-local API guarantee; no hostile-process isolation claim follows.

Keep current error/receipt vocabulary for authentication, forbidden or unavailable operations, invalid scope, revision conflict, revoked binding, backend/capability unavailable and unknown outcomes. Never turn unavailable into empty successful search or an acknowledged write. Canonical commit and index lag remain distinct.

## 5. One writer and real backend pluggability

### 5.1 Selection and cost

Mentle remains the canonical backend for the first private/shared-memory slice, reusing its shipped adapter and SQLite/outbox. Do not wait for a BML alternate, the full #7 enhancement backlog or a new Recap schema to deliver that slice. Preserve VIVY's separate BML-first validation and DIVA's Mentle default. Broader standalone backend swappability remains required: deliver a real qualified BML adapter as the separate S05 lane before claiming R3 complete, not as a hidden prerequisite for persona sharing, Mentle attachment, host/UI or setup work. Recommend independently accepted increments; whether alternate qualification must coincide with the broader v1 release remains owner decision Q2.

All subjects in an installation share one selected backend database; bound adapters are views, not separate stores. Selection is installation-level. Changes require explicit stopped-writer transfer/backup review; no hot fallback, dual write or independent-authority search aggregation. An existing BML-backed installation cannot be attached as a supported Garden writer until the BML lane qualifies; show that limitation rather than block existing Mentle attachment or silently convert data.

The current runtime makes model-less Mentle read-only or spools ingestion. That is inadequate for the broader fresh minimal-key wizard, but not a reason to block the sharing slice on an already working Mentle installation. Required setup integration delta: canonical CRUD and usable lexical retrieval must work without an embedding model; embeddings remain optional derived indexing. Coordinate the smallest no-embedding writable mode and Chinese lexical correctness with Laputa #1/#7, using existing facade/outbox. Do not copy their full enhancement backlog. If these prerequisites fail, report setup/backend not ready; do not invent a DeepSeek embedding endpoint or silently select BML. Owner may instead explicitly choose the qualified BML backend.

### 5.2 Shared contract and management reads

Preserve `memory.Backend` Search, Expand, Mutate, MutationStatus, Health, Close and existing exact scope encoding. Mandatory conformance includes bounded cards/evidence, stale-revision failure, source provenance, canonical revision/CAS, durable same-payload replay, changed-payload conflict, tombstones, scoped receipt lookup, restart recovery and honest canonical/index outcomes. A provider may use different ranking or native content formats; Garden does not prescribe Tencent levels or a universal fact taxonomy.

Garden resolves private scopes plus named shared-resource scopes into bound adapter views over the same selected database; it never grants another persona’s private scope. Use one view per admitted storage key, query only those scopes and merge bounded card pages using stable rank/order and scoped continuation state, then validate every result. This preserves the current Mentle adapter’s foreign-subject rejection and single write destination. Read-only membership never obtains a writable shared adapter; read_write permits an explicitly selected shared target. Bound fan-out/result budgets in configuration, report truncation, and invalidate continuation on membership changes; no cross-backend federation or unbounded global search is introduced.

The interface currently lacks full management browsing/history. Add a small **proposed management-read extension** beside it: paged item listing by exact scopes, current item lookup, revision listing/read and scoped collection metadata. Advertise these capabilities explicitly; each backend offered with full management support must implement the required UI reads. Scope this extension to actual UI needs; optional global enumeration, graph or trace methods do not become mandatory backend capabilities. Do not fake listing through an unverified empty-query search or keep `ListCollections` on raw Mentle. Canonical record/revision history remains in the selected backend; Garden may retain mutation audit metadata but not a shadow content ledger. Older embedded consumers keep the base interface. Add the management extension as needed for the full S12 UI and alternate qualification; it is not a reason to delay S03's minimal sharing UI on unrelated global/history APIs.

The current Mentle `Mutate` also restricts source refs to the adapter's admitted read union. For a user-selected private experience → new shared fact, preserve that private source reference without making the source readable to shared members: Garden validates the author’s exact source access, and a narrow adapter mutation-source input may admit only those operation-selected refs while leaving its shared read union unchanged. This is provenance validation for one explicit write, not persistent cross-private grants or inherited record ACLs. The minimal sharing slice can first accept user-authored shared information with its own provenance; cross-scope source-linked fact saving belongs to S07 and must not claim success until this delta is supported. Never silently drop lineage to make a write pass.

Required mutation receipt stays in the canonical transaction; derived index failure reports committed/degraded, not failed/no-write. A timeout requires status lookup with the same operation ID before retry. Source refs are typed backend/Journal references with revision/range and access requirements; no arbitrary URL/file fetching during expansion. Foreign refs require explicit resolver authorization. ## 6. Subject Recap, context admission and explicit facts

Keep one `ACTMEM.MD` authority/revision stream per subject through Laputa, containing free-form active Recap plus non-content revision/provenance metadata. No per-session recap copies, no UI-local authority, no backend record posing as ACTMEM. Reuse Laputa's revision/history/CAS machinery; update the existing ACTMEM owner rather than introduce a second store. Proposed storage grammar is `actmem/v3`: existing YAML front matter conventions carry schema, subject, revision, parent revision, updated time, operation ID/digest, coverage and clear generation; the body is one free-form Markdown Recap, without required Pulse/Work fields. Metadata and body commit as one document. Write an immutable revision snapshot before atomically replacing the head, with file/directory durability; only revisions reachable from the committed head count as committed history/receipts, so a crash-created orphan cannot acknowledge a write. Reuse existing filesystem/CAS helpers and add only missing revision-history durability. Metadata is not independently writable. Older v1/v2 content is owner-inspectable historical material until an explicit reviewed conversion; no active dual-read/fallback into old Work semantics.

A session records admitted Persona/Frozen Core revision and Recap revision separately. Subsequent Persona edits affect a new admission, not already frozen session content.

**Restricted-workspace proposal for review (Q3):** withdraw the initial draft's mandatory whole-Recap source-union/derived-access system. Keep one subject-private Recap and use a conservative input/admission rule instead: only a trusted session configured for that subject's personal-only context may automatically contribute; sessions enabled for shared or restricted-workspace material do not automatically consolidate into it. Consolidation-eligible sessions cannot fetch those other domains while contributing. Narrower sessions lacking personal-scope admission receive no Recap; all admitted same-subject sessions still address the same revision stream. Human edits remain explicit owner actions. This is a static host-policy boundary, not tracking or declassifying every model-derived sentence, and does not promise prevention of paraphrasing by arbitrary hosts.

This least-cost option limits mixed-source continuity and is **not yet owner-approved**. ADR-0018/#58 still require restricted-workspace safety; issue #8 deliberately does not redefine it. Broader mixed-source Recap consolidation needs a separately reviewed concrete policy, not automatic adoption of run-wide taint machinery. The first Mentle sharing slice can retain the existing scoped ACTMEM behavior and keep the new consolidation policy unenabled until that decision; it must still prevent cross-profile access and automatic private-to-shared writes.

VIVY owns its existing context policy, budgets, segment selection and summarization. Garden exposes authorized Recap read/CAS/clear and covered-source metadata; it adds no scheduler or second compactor. A retiring raw segment remains active until the new Recap commit succeeds. Conflicts return current revision; regenerate/review against that revision rather than blindly replay stale text. Concurrent sessions share the same stream and operation receipts; crash recovery uses committed coverage, not a session's optimistic watermark. No invented token/latency targets; tune on representative Chinese conversations with recorded model input and call cost.

Active clear commits an empty revision, increments a projection generation and establishes a consolidation coverage barrier. Invalidate cached projections and deny replay from older generations. Do not automatically reseed from pre-clear archives or already-covered evidence. A later explicit owner-selected restoration/reconsolidation may use retained sources; new post-clear segments may consolidate normally. Raw history, old Recap revisions and backend records remain until separately targeted deletion. Old prompt text already delivered remains in host history; native clients invalidate at their next context boundary, external hosts may require a new session.

Recap agent-management tools are normally absent. Reuse VIVY’s existing deferred tool search/activation and visibility middleware in [internal/runtime/engine.go](https://github.com/ProjectViVy/agent-vivy/blob/65b561f6f8189dc36dd29120a6f8a5f20b7071a6/internal/runtime/engine.go), with trusted binding/operation checks at the owning API; do not add a second discovery framework. This machinery is source evidence, not proof that ACTMEM tools are already integrated. A small discoverable catalog may describe names/capabilities without their schemas; trusted host activation enables a session-bound operation and exposes only the requested inspect/update/clear schemas. Human-authorized write/clear remains CAS-bound. Hosts unable to defer schemas use explicit owner UI/MCP connection activation for this tool group; do not advertise transparent deferred discovery there. Automatic Recap injection is LIFE-first in VIVY, CODE excluded. Supporting Claude/Codex explicit persona/memory tools does not authorize VIVY CODE resident Recap or external coding-host autonomous consolidation.

Selected experience → fact is a separate, simple flow: choose authorized evidence/range → optionally draft a fact using DeepSeek → inspect content/provenance/scope → explicitly save through backend Mutate. Capture-enabled hosts may submit a selected bounded completion event with stable identity; capture does not promote every summary into a fact. UI shows queued/captured/draft/saved distinctly. No automatic pin, Persona mutation, skill generation or rules change follows fact save. Human must-not-forget requests go to existing Laputa edit/review, with Mission/Dream restrictions preserved.

## 7. External hosts: consent, mapping and phase-one acceptance

### 7.1 Common binding lifecycle

Discovery is read-only; installation places inert adapter files only. Bindings start disabled. Owner review selects host instance, persona, workspace, exact paths/config changes, operation limits and independent `persona_sync`, `recall`, `capture` switches. A file adapter credential has only the memory operations required; the owner authorizes file writes via Garden, not a model-generated instruction. Disabling a switch removes that future capability without enabling another. Revoking the binding revokes credentials and queues; attempts to restore managed files use conflict-aware cleanup, with manual recovery if the user changed them.

Persona mapping is an approved projection of selected existing Persona documents, labeled with subject and source revisions. Default proposal: Identity/Relationship/Redline/User and explicitly selected Dream/Dark; Mission is separately owner-selected; WORLD/Recap are never silently added to static persona files. Show exact rendered content before first activation and when the approved document set changes. Do not claim host instruction precedence makes Garden's projection authoritative over system/project instructions.

For each managed file/block retain original hash/backup, last written whole-file hash, managed-region hash, target revision and adapter version. Re-read and compare before writing; use atomic replacement and the host's compare-and-set API where provided. Preserve all content outside marked Garden regions. A conflict stops writes and offers a diff/rebase or restore choice; never overwrite unknown project/user instructions. Backups are host-side private files, not content served through memory APIs. No self-modifying rule hooks.

Track **saved** (canonical Persona revision), **written** (exact projection/file hash and revision), **loaded** (only a host/session-qualified acknowledgement of the exact projection). A successful file write or hook invocation is not a loaded acknowledgement. Expose `pending_reload`, `unknown`, `conflict`, `revoked` explicitly. Hosts without proof of model admission show loaded unknown; “context submitted” is a separate weaker status. New sessions retain which revision was actually acknowledged. Revocation blocks future Garden access but cannot erase already delivered prompt history, files or transcripts; stale managed snapshots are visible until safely removed/reloaded.

## 8. First launch, DeepSeek, upgrades and UI

### 8.1 Persisted setup

First-launch state is a versioned row in Garden state DB, with step completion and last safe checkpoint. Proposed steps: (1) local owner pairing/home validation; (2) DeepSeek key; (3) storage readiness and optional existing-data choice; (4) optional first persona—attach, create or skip; (5) optional hosts; (6) finish. Only key entry is needed in the normal provider step; endpoint/model have a reviewed shipped default, shown in advanced settings. A skipped persona/host is valid completed setup. A skipped/failed key leaves model-dependent actions unavailable but permits explicit offline completion; normal management remains usable. On restart resume incomplete setup; after finish open console, never rerun wizard because a key expired or a backend became unhealthy.

Use fixed HTTPS DeepSeek endpoint `https://api.deepseek.com` for initial testing, without a general provider chooser or proxy. The [official first-call page](https://api-docs.deepseek.com/) checked on 2026-10-12 documents `deepseek-flash` and `deepseek-v4-pro`; propose the documented Flash identifier as the initial low-cost candidate, subject to account/model availability check at release and wizard validation. This is not a price/performance measurement or an immutable model promise. Send the native provider model ID, never a gateway prefix. No embedding API is assumed. A small explicit test request uses synthetic content, not private memory, and reports access/model errors truthfully.

Secret default: an owner-only host-side file in the private Garden home (directory 0700/file 0600 on Unix; equivalent owner ACL on Windows), referenced by ID from non-secret config. This uses existing filesystem facilities and avoids a mandatory vault dependency. Where a supported packaged OS credential store already exists, it may implement the same resolver. Environment-supplied key is supported without persisting the value. Never send the stored key back to the UI; never store it in localStorage, Persona, host instruction files, logs, export bundles or backups intended for sharing. Fail setup if private permissions cannot be established. Secrets are excluded from ordinary data exports; owner chooses separate protected backup/re-entry. The UI makes persistence choice visible (Q5).

### 8.2 Upgrade and failure ownership

Application schema version is distinct from onboarding completion, provider version and host adapter version. Startup checks versions under exclusive ownership; take a coherent stopped-writer backup before any approved schema upgrade. Supported metadata upgrades are transactional/restartable; backend and Persona format conversions use their owning libraries and an explicit preview when content/scope mapping changes. Never delete/reinitialize on parse failure, rerun first-launch as recovery, or silently migrate Pulse/Work into facts. Unknown versions fail read-only with a recovery explanation. Downgrade requires supported format compatibility or explicit restore, not opening new data with old code.

Backend health and model health are separate. Model failure disables generation only. Backend failure blocks new canonical writes and reports unavailable; reads are served only if the selected backend can honestly provide them. A capture queue is bounded, authorized transient work with explicit pending status; it is not a successful memory receipt or a fallback database. Shutdown stops intake, drains/cancels bounded work, closes stores and releases ownership. No background data conversion at boot.

### 8.3 Console interaction design

Reuse current shell/pages; replace single-profile assumptions with a persistent subject selector and installation status. No chat approval center is reused for Persona review. Wireframe-level flow:

```text
Garden  [Subject: VIVY v]                         [Backend: Mentle · available]
  Personas | Memory | Access & Hosts | Settings

Personas: list -> actual documents -> edit/diff -> save/review -> revision history
Memory:   Recap [full current revision | loaded per session | edit | clear | history]
          Records [scope/filter/search] -> card -> bounded source -> edit/history/delete
Access:   private scopes + named shared spaces -> participants/read or read_write
Hosts:    discovered (inactive) -> preview mapping/permissions -> enable independent switches
          saved r12 | written r11/hash | loaded unknown -> conflict/reload/revoke
Settings: provider/key status | selected backend/capabilities | setup/upgrade/backup status
```

Recap editor shows the complete active revision, pending edit, CAS conflict and source coverage; owner may compare and resubmit, never silent overwrite. Clear dialog names only the active target and preserved history; source/backend deletion is a separate target. History restore creates a new current revision. Memory detail distinguishes source event time, capture time, revision and provenance; edited facts keep lineage without pretending the original evidence changed. Permission-filtered or unavailable sources are visibly incomplete without exposing hidden titles. Host status does not claim model-loaded state from server saves. Zero-persona state offers create/attach; management works without a model. Backend selection shows required capability checks and a deliberate transfer requirement for existing data.
